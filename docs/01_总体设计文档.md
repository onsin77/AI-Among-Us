> 生成日期:2026-10-19。前置阅读:《00_源码导读笔记.md》。

## 1. 系统架构

```
┌─────────────────────────────────────────────────────┐
│ L3 Agent 程序 (Python 3.10+ / FastAPI / 浏览器 UI)    │
│  行为引擎(goals状态机) + DeepSeek网关 + 会议代理 +    │
│  世界模型 + 记忆库 + 面板                            │
└───────────────┬─────────────────────────────────────┘
                │ L2: JSON 行协议, TCP 127.0.0.1:47600
┌───────────────┴─────────────────────────────────────┐
│ L1 游戏内 Mod (C#, BepInEx 插件, IL2CPP interop)      │
│  AIHub 单例: 采集器(10Hz) + 执行器 + 自动任务 +        │
│  事件发射器 + waypoint寻路 + TCP服务端                │
└─────────────────────────────────────────────────────┘
```

分层理由与说明书一致:L1 只做确定性游戏操作与数据读取,L3 做 AI 编排;L2 用 **本地回环 TCP**(决策见 §2.2)。文件通道仅用于会议文本与记忆持久化。

## 2. 关键架构决策(⚠️ 需你确认)

### 2.1 ⚠️ 决策 A:L1 代码的宿主形态

| 方案 | 做法 | 代价 | 评估 |
|---|---|---|---|
| **A1(推荐):并入 TheOtherUs 源码树,新增独立目录 `TheOtherRoles/AIAmongUs/`** | 与 mod 同程序集编译,一个 Harmony 实例,直接访问全部职业静态字段/RPCProcedure/PlayerData | mod 升级需 merge(本 mod 版本已冻结 1.2.9.8/2023.11.28,实际无升级压力);构建链复用现有 csproj | 全职业适配需要读 internal 成员、与 mod patch 协调 Harmony 优先级,同程序集最省事、最不易踩 IL2CPP 跨程序集坑 |
| A2:独立 BepInEx 插件,引用 TheOtherUs.dll | 代码隔离干净 | 跨程序集访问受限(public 可访问,RPCProcedure 等 internal 需反射);两个 Harmony 实例的 patch 顺序更难控;需自建 csproj+interop 引用链 | 职业全覆盖时反射面大,长期维护成本更高 |
| A3:改 mod 既有文件内嵌逻辑 | 零新增结构 | 污染 mod 源码,不可维护 | 否决 |

**推荐 A1**。所有新代码集中在 `TheOtherRoles/AIAmongUs/` 命名空间 `AIAmongUs` 下,不改动 mod 既有文件(唯一例外:csproj 增加编译目录、build.bat 改输出路径)。

### 2.2 ⚠️ 决策 B:L2 通道选型

| 方案 | 优点 | 缺点 |
|---|---|---|
| **B1(推荐):TCP 127.0.0.1:47600** | Python asyncio 原生支持;可用 telnet/nc 手测;无管道权限/编码坑;断线重连语义清晰 | 端口可能冲突(可配置) |
| B2:命名管道 `\\.\pipe\au_ai` | 无端口冲突 | IL2CPP 下 System.IO.Pipes 可用但调试麻烦;Python 侧需额外库;中文系统下管道名偶有编码问题 |

**推荐 B1**,端口写入 L1 的 mod 配置与 L3 的 config.ini,两侧可改。协议:每行一条 UTF-8 JSON(无 BOM,`\n` 分隔)。

### 2.3 ⚠️ 决策 C:移动与寻路方案

游戏无 navmesh、无点击移动。方案:

| 方案 | 做法 | 评估 |
|---|---|---|
| **C1(推荐):手工 waypoint 图 + A\* + 直线段跟随** | 每张地图一张 JSON 数据(节点: 坐标/房间/类型[普通/梯子/平台/管道口];边: 连接+代价),A\* 求路径,节点间 `SetNormalizedVelocity` 直线跟随,到达容差 0.35f | 完全可控、可调试(图可在面板可视化);一次性数据工作量大(飞艇 ~150 节点),但一次做好永久复用;梯子/平台作为特殊边类型处理 |
| C2:运行时从房间 collider 自动生成可视图 | 无手工数据 | 房间形状不规则,生成质量差,角落卡死难调;调试成本远超手工 |
| C3:直接位置插值+穿墙(RpcSnapTo 连发) | 最简单 | **穿帮+非 host 不生效+被当作外挂**,否决 |

**推荐 C1**。waypoint 数据的制作:迭代 1 我先用源码里的坐标参考(任务点 console 坐标、房间中心)+ 游戏内采样工具(L1 加一个 debug 指令:站在原地按热键记录当前坐标存文件)半自动完成。**飞艇(Airship)P0,Skeld P1,其余 P2**(你已指定飞艇优先;Skeld 顺手因为最简单)。

### 2.4 其余既定决策(按说明书,不再列选)

- AI 大脑 = DeepSeek V4.1 flash(运行时),fast 档 ≤200 token / ≤800ms 端到端 / 超时降级脚本;deep 档会议用。
- 会议文本走 `meeting_input.txt` / `meeting_output.txt` + `POST /turn` HTTP 双保险。
- `round` 全局唯一定义:**已开过的会议次数 + 1**(开局即 round=1,第一次会议后变 2)。事件、会议、记忆三处统一。

生命周期规则(对应坑清单第 3 条):
- AIHub 持有当前 phase 的唯一判定(§3.2);所有协程/计时器挂 `CancellationToken`,phase 切换(MEETING↔PLAYING、游戏结束、回菜单)统一 cancel + 清栈;
- TCP 连接断开:仅停止"指令执行",采集器继续缓存最近状态(重连立即全量同步);
- Minigame 打开/关闭驱动 TaskPrivilege 计时器挂载/卸载。

### 3.2 Phase 状态机(L1 侧权威,L3 跟随)

```
MENU → LOBBY → PLAYING ⇄ MEETING → PLAYING ... → ENDED
                ↑IntroCutscene 期间 = PLAYING 的 intro 子状态
```

判定函数(每 tick 重算,来源见导读笔记 1.5):

```csharp
Phase GetPhase() {
  if (AmongUsClient.Instance.GameState == NotStarted) return Lobby;
  if (AmongUsClient.Instance.IsGameOver || ExileController 场景 EndGame) return Ended;
  if (MeetingHud.Instance != null || ExileController.Instance != null) return Meeting;
  if (HudManager.Instance.IsIntroDisplayed) return Playing(intro);  // 快照里 intro=true
  return Playing;
}
```

MENU 与 LOBBY 的区分:`AmongUsClient.Instance.CurrentScene` / 是否在大厅场景。**每条下行指令都有 phase 白名单,不在白名单 → ack err="phase_guard"**。

### 3.3 状态采集(10Hz,增量协议)

两级消息:
- **`state_full`**:1Hz 或 phase 切换/重连时发(全字段);
- **`state_delta`**:10Hz,只含变化字段。首版实现:位置类字段每 tick 必发(浮点用 2 位小数),其余字段脏标记(与上次比较,变了才带)。序列化压力预估:15 玩家 × 位置 2 float ≈ 600B/条,10Hz = 6KB/s,可接受,暂不做位压缩。

schema(以 `state_full` 为准,delta 为其子集;字段语义与说明书一致,按源码实际可得微调):

```jsonc

  "round": 2, "phase": "PLAYING", "intro": false,

  "me": {
    "player_id": 3, "color": "Red", "name": "AI-Red",
```

| 指令 | 参数 | phase 白名单 | 实现 |
|---|---|---|---|
| `move_to` | `{pos:[x,y]}` 或 `{room:"Electrical"}` 或 `{node_id: 42}` | PLAYING | Pathfinder 寻路+跟随;执行中收到新 move_to 覆盖 |
| `move_stop` | — | PLAYING | 速度清零 |
| `use_ladder` | `{ladder_id}` | PLAYING | RpcClimbLadder(寻路自动调,也可手动) |
| `use_platform` | — | PLAYING | RpcUsePlatform+等待 |

| `kill` | `{target_id}` | PLAYING | 有 mod 职业刀→RpcCustomMurderPlayer;否则 CmdCheckMurder。**L3 连发模式,L1 每 100ms 尝试一次直到收到击杀确认事件,或 3s 超时回执失败** |

### 3.5 自动完成任务特权(TaskPrivilege)

流程(严格按说明书 3.3):
1. L3 发 `open_task {task_id}` → L1 校验 `task ∈ LocalPlayer.myTasks 且 !IsComplete`;
2. 寻路至该任务当前阶段 console(多阶段任务用 `ValidConsole`/Locations 定位**当前 step 的位置**);
3. 距离 < usableDistance → 调 `console.Use()`(真实打开面板,他人可见);
4. 面板打开(`Minigame.Instance != null` 且 MyTask.Id == task_id)→ 启动 10s 计时(挂在 minigame 实例上:`Minigame.Instance` 被换/销毁即取消);
5. 计时到 → 逐阶段推进:`task.NextStep()`(一次只推一步,多阶段任务回到 4 等下一轮,间隔随机 8~14s,外观与真人一致);最终步由 NextStep 内自动 `RpcCompleteTask(Id)` 完成网络同步;
6. 全程发 `TASK_*` 事件;若面板被人为关闭→ 发 `task_aborted` 事件,L3 决定重试。

边界自查(实现时的断言):死亡后指令拒绝(`dead`);task_id 越权拒绝;会议中指令拒绝(phase_guard);别人视角:我们只调 `console.Use()` 与 `NextStep()`,与真人操作调用链完全相同,不存在"远程完成"路径。测试用例(迭代 2 执行):a) 有旁观者在场做任务(旁观者任务面板不受影响,b) 中途关面板,c) 死亡后发指令,d) 会议中发 move_to,e) 完成一个多阶段任务(Wiring 三段)全程事件流核对。

### 3.6 事件采集(EventTap)

双层来源:
1. **mod 现成事件**:`GameDataManager.EventLog`(SetRole/CustomMurderPlayer/MeetingStart/ClearVote 已有)→ 桥接;
2. **自建 patch**(全部 Postfix 不改返回值,优先级低):`PlayerControl.MurderPlayer`(击杀)、`DeadBody` 生成(钩 KillAnimation 后)、`PlayerControl.ReportDeadBody/CmdReportDeadBody`(报告/紧急)、`ShipStatus.UpdateSystem`(破坏/修复)、`Vent.EnterVent/ExitVent`、`MeetingHud.Confirm`(投票)、`CustomButton.onClickEvent`(自己用技能,或挂 `Cartethyia.OnLocalAbilityUsed`)、玩家死亡/复活(ExileController.WrapUp + Die)。

产出统一事件(上行),schema 见 §6。

### 3.7 与 TheOtherUs 的 Harmony 共存

- 我方 patch 类全部 `[HarmonyPriority(Priority.Last)]` Postfix(除必须捕获参数的 prefix 场景,如 MeetingHud.ServerStart 记录 reporterId——该处 mod 已有 First 优先级 patch,我们用 Last prefix 只读取不入逻辑);

## 4. L2 协议规范

- 传输:TCP `127.0.0.1:47600`(可配),L1 为 server(L3 为 client,断线 1s 重连);
- 编码:UTF-8 无 BOM,每行一条 JSON,`\n` 结尾;
- 消息分向:上行(L1→L3)= `state_full / state_delta / event / ack / log`;下行(L3→L1)= §3.4 指令 + `ping`;
- 序号:下行指令带 `ref`(自增 int),ack 原样带回;
- 心跳:双方 5s 一次 ping/pong,10s 无响应判定断连。

### 5.1 行为引擎

- 事件驱动:上行消息进队列,引擎逐条处理;`state_delta` 更新世界模型,`event` 触发决策钩子;
- 决策优先级(严格顺序):
  1. **硬覆盖**:尸体报告(好人/无刀中立,无条件)/ 被追杀逃跑 / 会议强制中断当前目标;
  2. **锁定的主目标**(weight=100%);
  3. **goals 采样**:非极端权重归一化采样选主目标;
- 主目标生命周期:完成 / 硬覆盖打断 / 30~60s 定时器 → 重评估(规则优先,AI 可选);
- fast AI 仅在:杀人决策触发(视野内出现存活玩家且我是刀)、目标重评估(可配置关)、可疑局面(可后置)。**默认无 AI 纯规则可跑**(迭代 3 验收要求)。

结构同说明书。动作库(初版):

| `fake_task` | room, duration(15-25s 随机) | 走到任务点站桩,不开面板不推进 |
| `hunt_kill` | mode: opportunistic/patrol/follow | 找落单目标→接近→kill 连发 |
| `hide` | — | 走向偏僻 waypoint(数据里标注 `secluded:true` 的节点) |

### 5.3 AI 网关(DeepSeek)

- fast 档:`deepseek-v4.1-flash`,`response_format=json_object`,`max_tokens≤200`,禁思考,超时 800ms 端到端(连接 3s/读 0.8s 里的读预算),失败→规则默认行为,并记 `ai_fallback` 决策日志;
- deep 档:会议/复盘,允许长输出,超时 30s,失败→保守模板发言("我没什么信息,跟票");
- 统一决策日志:触发原因、输入摘要、输出、耗时、token 数(面板可见+存档)。

## 6. 事件系统 schema(含 TOR 扩展表)

> ⚠️ 基准假设:`among_us_event_catalog.md` 未提供,字段按说明书规范 `t/code/actor/target/loc/vis/note` 设计。**你提供原文件后对齐事件 code 命名与收录标准。**

每条事件:

```jsonc
{"type":"event","t":123.4,"round":2,"code":"KILL",
 "actor":"AI-Red","target":"Pink","loc":"Electrical",
 "vis":["Blue","Yellow"],        // 除 actor 外可目击者(id 列表;不可精确判定时给 room 内玩家)
 "note":"kill_distance=1.8"}
```

### 6.1 原版事件(code 首版,语义对齐说明书)

| code | 触发 | note |
|---|---|---|
| `GAME_START / GAME_END` | 开局/结束 | 开局带 map/role 分配(仅我方已知部分) |
| `INTRO_END` | 我可行动 | 身份/任务清单快照 |
| `TASK_START / TASK_STEP / TASK_DONE / TASK_ABORT` | 特权任务链路 | step 信息 |
| `KILL` | MurderPlayer | 距离/是否目击 |
| `DEATH / EXILE / REVIVE` | Die/Exiled/mod 复活 | death_reason(mod CustomDeathReason) |
| `BODY_FOUND / BODY_REPORT / EMERGENCY_MEETING` | 报告 | reporter |
| `SABOTAGE_START / SABOTAGE_FIXED / DOOR_CLOSED` | UpdateSystem | 类型/房间 |
| `VENT_ENTER / VENT_EXIT / VENT_MOVE` | 管道 | vent id/连线 |
| `MEETING_START / MEETING_END` | 会议 | round 递增点=MEETING_START 后 |
| `VOTE / VOTE_RESULT` | Confirm/CalculateVotes | 我可见的票面 |
| `PLAYER_SEEN` | 视野内出现玩家(节流:进出视野沿) | 距离 |
| `ROOM_ENTER` | 我换房 | — |
| `CHAT` | 会议发言 | 频道 |

### 6.2 TOR 扩展事件(`TOR_` 前缀,全职业感知——第一版按"可观测"优先)

从 CustomRPC 枚举 + Objects 目录梳理,分三档:

- **P0(迭代 4 必做,影响决策)**:`TOR_KILL_VARIANT`(处刑/吸血/吞食/处刑者处决等,统一 KILL 变体+note 职业)、`TOR_CLEAN_BODY`(清理者)、`TOR_SHIELD_BLOCK`(医生盾/保镖,我可感知的弹刀)、`TOR_MEETING_ABILITY`(检察官起诉/市长揭示/换票——影响我的票)、`TOR_SABOTAGE_MOD`(榴弹闪/灯黑等 mod 破坏)、`TOR_TRAP_TRIGGER`(陷阱类可见效果)、`TOR_CAMO`(全场同皮肤化)、`TOR_MORPH`(有人变形/被模仿)、`TOR_HANDCUFF`(我被铐)、`TOR_BLACKMAIL`(我被勒索)。
- **P1(迭代 5 会议推理需要)**:`TOR_ROLE_CLAIM`(有人跳身份)、`TOR_GUesser_SHOOT`(会议猜人+结果——直接影响赌怪风险)、`TOR_VENT_EXTRA`(mod 加装管道)、`TOR_PORTAL/BOMB/DECOY 等物体生成与触发`。
- **P2(完整性,后续补)**:其余物体/修饰表现。

《mod 事件扩展表》作为独立交付物在迭代 4 随事件系统一并交付(格式同上表,逐职业从源码 RPC 表补全)。

### 6.3 事件流向

L1 EventTap → L3 world_model.EventLog(全量)→ 面板事件流渲染 + 会议代理输入 + 存档。**Agent 自身行动事件与观测事件都进流**(字段里 actor 区分),会议里"我的脚程"由 L3 从自身行动事件抽取。

## 7. 会议系统(L3 meeting/proxy)

- 输入通道:`meeting_input.txt`(人类追加写)、`POST /turn {"player_id":3,"is_me":true}`(换轮通知)+ `turn_control.json` 双保险;输出:`meeting_output.txt`;
- MEETING phase 到达:暂停行为引擎、快照会议元信息(reporter/order 从 L1 `state.meeting` 拿,order 由 L3 按"报警人开始、从左到右从上到下"生成=玩家 id 升序);
- 轮到我(收到 turn is_me=true):**立即**组织发言——发言内容在等待期间已用 deep 档预生成(听到每条新发言后增量更新推理),轮到时仅做最终选择;
- 输入组装:开局元信息+全事件流+发言记录+lessons 相关条目 → deep 档产出三件套:
  1. 阵营视角表(好人:内鬼权重表;坏人:好人身份推断+安全脚程校验——**先核对事件流里我被目击记录,编造行程不得与之冲突**)、
  2. 发言文本+`claim_role` 决策(真跳/假跳/模糊;默认好人不主动跳;有赌怪风险信号(TOR_GUesser_SHOOT 历史或模式开启)时倾向模糊)、
  3. 投票意向(权重表最高者;坏人:投威胁者或跟风);
- 投票执行:所有人发言完/turn 通知到投票阶段 → 发 `vote`;
- 会议收尾:goals 重设定(结合职业:警长→hunt 杀怀疑对象;隐身类→use_ability 目标房间;好人→剩余任务/follow;内鬼→sabotage/双杀节奏),MEETING_END 时写入并恢复行为引擎。

## 8. 记忆系统

- `memory/games/YYYY-MM-DD_N.json`:开局配置(地图/身份/职业参数)、完整事件流、AI 决策日志(每次调用的输入摘要/输出/耗时/token)、goals 演变、胜负死因;
- `memory/lessons.md`:条目 `## L<阵营>-<场景> → <教训>` + 元数据(来源局号、验证状态 active/disputed/retired);
- 局后复盘(deep 档):输入本局存档+现有 lessons → 输出增量条目+对旧条目的证伪标记;人可在面板确认后入库(默认自动入库,面板可撤);
- 下局开局:按我的阵营/职业过滤相关 lessons 注入 system prompt(条目数上限 20,防膨胀)。

## 9. 面板 UI(FastAPI + 单页)

## 10. 全职业适配策略(响应"角色必须尽量全适配")

三层解耦,保证覆盖面与深度兼顾:

| 层 | 覆盖 | 方案 |
|---|---|---|
| **感知层**(事件) | 100%(约 110 RoleId) | EventTap hook 全部 CustomRPC 接收路径 + CustomButton 点击 + 物体生成——粗粒度但无遗漏;TOR 事件表 P0/P1/P2 分批细化 |
| **行动层**(用技能) | 100% | `abilities` 枚举 CustomButton.Buttons;`use_ability {key}` 统一触发;会议类走专用指令——无需 per-role 代码 |
| **策略层**(用好技能) | 分批 | 第一批(迭代 4-5):警长/豺狼/医生/工程师/黑客/吸血鬼/清理者/赏金猎人/小丑/幸存者 等高频职业的专属 goal 模板与参数;第二批:会议技能型(检察官/市长/换票/赌怪);第三批:长尾职业用通用策略(按钮 ready 且情境匹配即用) |

每个职业的最小适配单位 = 一份《职业适配卡》(role_id / 阵营 / 刀 / 按钮 key 列表与语义 / 推荐初始 goals / 可见表现事件映射),作为迭代 3-5 的滚动交付物,首批 20 张随设计确认后产出。
